## Explicit decision on PR #44

**Safe within this audit:** fail closed when a limiter read, initialization, reset, or counter validation fails. Compass returns 503 for an unavailable guard (429 for quota denial) before context reads/generation. Await recording immediately after a successful generation, before conversation saving, so failed saves and serverless response completion do not skip the normal accounting attempt.

**Deliberately deferred:** atomic request/token reservation, independent minute/day windows, recovery/reconciliation, and accurate streaming accounting. Replacing the shared limiter affects multiple routes and existing documents; it needs schema compatibility, contention/emulator tests, failure recovery, cancellation handling, and token-budget semantics. Estimate **2–4 engineering days plus a day of staging validation**, beyond a narrow last-minute safety patch. Partial atomic increments alone would not fix the admission race or reserve future tokens.

Residuals are **high severity**: successful reads with failed recording still undercount (`recordRequest` logs and swallows write failures); missing provider usage records zero; concurrent requests can all pass; daily initialization can race/reset counters; streaming failures/estimates undercount; deleting and re-creating accounts provides new UID budgets. The full fix may be deferred **only if an enforced aggregate OpenAI limit and operational response are verified before launch**. Otherwise this remains a launch blocker. This PR does not claim the limiter is atomic or that every accounting failure now fails closed.

## Code changes in this PR

- `app/api/gpt/utils/rate-limiter.ts`: deny guard failures and malformed counters; expose unavailable status. Existing numeric thresholds and window semantics are unchanged.
- `app/api/ai/route.ts`: distinguish unavailable guard, and await usage accounting before conversation persistence. Write failure logging retains the existing response behavior; provider consumption cannot be rolled back.
- `app/api/gpt/utils/openai-client.ts`: `maxRetries: 0` and existing `TIMEOUT_MS` (30 seconds). Installed SDK otherwise defaults to two retries and a ten-minute timeout; a failed/ambiguous generation could be replayed. Normal successful payloads/models are unchanged; transient errors are surfaced for deliberate user retry.
- `app/api/ai/stream/route.ts`: pass a 30-second abort deadline to its raw provider fetch (including streamed body consumption). This bounds local waiting; it cannot guarantee provider-side cancellation or zero charges after cancellation. SDK timeout bounds request establishment/response waiting and is **not** a guaranteed total duration cap on every streamed body.
- `tests/launch-cost-risk.test.cjs`: exercise real modules with synthetic service boundaries, failure denial, single-attempt provider calls, accounting order, and raw-stream timeout.

**No response cache added anywhere.** Compass uses Current Focus, archetype, and conversation history. Shared or stale response caching would risk context leakage/incorrect advice. Durable request IDs scoped to UID/conversation and recovery would be a separate design, not prompt-based caching.

## Abuse and cost exposure

**One account:** send concurrent Compass requests before any finishes, exploit the broken minute window, retry after lost responses, or use legacy GPT with an expensive model. A paid account can use `/api/ai/stream` without daily accounting. Every rejected/requested action can still consume Vercel compute and some Firebase authentication/Firestore operations.

**Many accounts:** `mobile/src/context/AuthContext.tsx` calls Firebase `createUserWithEmailAndPassword` directly. Public client configuration is not a secret or proof of a genuine app. Neither `requireAuthenticated` nor Compass requires email verification, onboarding completion, payment, CAPTCHA, or App Check. A script can create accounts and call Compass with their ID tokens. Firebase documents 100 new accounts/hour/IP as a provider safeguard; it is not a shared application AI budget and distributed IPs defeat its aggregate protection. Even perfect UID limits permit N times the per-user spend. The public workshop endpoint also creates Firebase users through Admin SDK and sends account emails; it is a separate abuse surface. No live account-farming test was performed. [Firebase Auth limits](https://firebase.google.com/docs/auth/limits).

### Theoretical OpenAI costs (USD; not enforced spending caps)

Standard text rates verified September 27 from official model pages; actual deployment overrides, account discounts, provider availability and access must be checked by the owner. No cache discounts assumed. No tools, images, audio, embeddings or additional AI providers found in active call sites.

`cost = input_tokens / 1,000,000 × input_rate + output_tokens / 1,000,000 × output_rate`.

The following assumes **exactly 500,000 total accounted tokens per UID per 24 hours**, successful accurate accounting, no overshoot/retries, and at most 1,000 requests. Input-only and output-only figures are mathematical bounds, not realistic chat mixes. Thirty days is the comparison month; October has 31 days.

| Model / route default | $ / 1M input / output | Per UID/day bound | Per UID/30 days | Per UID/October (31 days) |
| --- | --- | --- | --- | --- |
| [gpt-4o-mini](https://developers.openai.com/api/docs/models/gpt-4o-mini), Compass | $0.15 / $0.60 | $0.075–$0.30 | $2.25–$9 | $2.325–$9.30 |
| [gpt-4-turbo-preview](https://developers.openai.com/api/docs/models/gpt-4-turbo-preview), legacy GPT stream | $10 / $30 | $5–$15 | $150–$450 | $155–$465 |
| [gpt-4](https://developers.openai.com/api/docs/models/gpt-4), legacy GPT non-stream | $30 / $60 | $15–$30 | $450–$900 | $465–$930 |

The stream row is hypothetical accurate token accounting; its actual estimator misses input and cannot support that cap. Configured `gpt-3.5-turbo` is a fallback constant, not an automatic fallback call in `gpt-core`; it is not added as separate spend.

For Compass at an illustrative 80% input / 20% output split, 500K tokens cost **$0.12/day, $3.60/30 days, $3.72/October per account**. That fits the request/output bounds (e.g. 200 requests at 2,000 input + 500 output tokens each).

| Accounts exhausting that illustrative UID allowance daily | Daily | 30 days | October |
| --- | --- | --- | --- |
| 100 | $12 | $360 | $372 |
| 1,000 | $120 | $3,600 | $3,720 |
| 10,000 | $1,200 | $36,000 | $37,200 |

At the conservative $0.30/day token-price bound, 1,000 accounts instead imply **$300/day / $9,000 per 30 days / $9,300 in October**. At the same 80/20 mix, legacy `gpt-4` costs **$18/day / $540 per 30 days per UID**, or $18,000/day for 1,000 accounts, if provider capacity permits. These routes share the UID allowance; their rows are alternatives, not additive independent allowances.

Request-only sensitivity: 1,000 Compass calls × 1,024 output tokens = 1.024M output tokens = **$0.6144/day plus input**, if token accounting fails but request accounting works. History/context/system prompts are input on every call. The intended 60/min implies 86,400 requests/day and 90K tokens/min implies 129.6M tokens/day absent the daily limits; neither is a global cap. With races, undercounting, unlimited `/api/ai/stream`, arbitrary legacy models, and unlimited accounts, **there is no finite total daily/monthly application-code ceiling**. Actual provider throttles/access and manual spend controls are decisive, not a numeric “worst-case” derived from broken counters.
